# S3Harp design

This document records the agreed design and its open questions. It states intent — see the [README](README.md) for what actually works today. When a decision here changes, this document changes with it.

## Purpose

S3Harp serves two uses, and the tension between them keeps the project honest:

1. **A local S3 stand-in for development and testing** — spin it up, run code against it, throw it away.
2. **Real self-hosted storage** — trusted with actual data on the owner's hardware, which makes correctness and durability requirements.

## Scope

- **Core S3 essentials:** buckets, object PUT/GET/HEAD/DELETE, ListObjectsV2, multipart uploads — the whole current scope. The wider API surface (versioning, lifecycle, ACLs) becomes candidate work once the core is solid.
- **AWS Signature Version 4 from the start.** SDKs sign every request; auth cuts deep into request parsing and is foundational. This includes the streaming forms (`aws-chunked` / `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`, and its `-TRAILER` variant carrying trailing checksum headers, which current SDKs send by default, plus `STREAMING-UNSIGNED-PAYLOAD-TRAILER`, the same framing without chunk signatures that SDKs switch to over TLS): the AWS CLI and SDKs send chunked bodies on PUT, so decoding and verifying every form is what keeps real clients working.
- **Single-node, by design.** S3Harp runs on one machine and one filesystem — a permanent scope decision the architecture is free to build on.
- **Standard-region S3 semantics.** Where S3's behavior differs by region, S3Harp follows the standard regions: creating a bucket you already own returns 409 `BucketAlreadyOwnedByYou`.
- **Both addressing styles.** A bucket is named either by the path (`/bucket/key`) or by a host label under the configured domain (`bucket.localhost/key`), decided per request from the Host header. SDKs default to the virtual-hosted form, and `*.localhost` resolves to loopback everywhere, so the default domain needs no DNS.
- **User metadata is UTF-8 on the wire, in both directions.** `x-amz-meta-*` values arrive as UTF-8 bytes and are returned as the same bytes, which is the only encoding that can carry every character a client may store.

## Architecture

Two production projects, one seam between them:

- **`S3Harp.Core`** — the storage engine, a plain .NET library: buckets, object storage, multipart state, the on-disk layout, copy-on-write use.
- **`S3Harp.Server`** — the S3 HTTP layer on ASP.NET Core/Kestrel: SigV4 verification, request dispatch, XML serialization. Depends on Core.

The split exists because the HTTP protocol surface and the storage engine evolve at different speeds, and because each is testable on its own.

### Request dispatch

S3 routes on verb + path shape + query-string markers (`GET /bucket?list-type=2`, `POST /key?uploads`, `POST /key?uploadId=…`). The server uses a small explicit dispatcher over S3's finite operation table — a direct match for that routing model.

### Object storage

S3 object keys are up to 1024 bytes of arbitrary UTF-8, so S3Harp treats them as pure data: every key reaches storage through the metadata index, and file names on disk are generated by S3Harp, keeping arbitrary key bytes away from path semantics entirely.

- **Blob store:** object data lives in plain files on the local filesystem, each named by an opaque generated identifier. One object owns one blob, which keeps deletion trivially correct.
- **Metadata index:** a separate index maps key → blob and carries object metadata, providing the lexicographically ordered range scans that ListObjectsV2 requires.

Durability discipline applies from the first write path: write to a temp file, fsync, rename into place, fsync the directory.

Where the filesystem supports copy-on-write reflinks (btrfs, XFS, ZFS block cloning), object copies and multipart assembly share blocks rather than rewrite bytes; everywhere else the same operations use ordinary copies. CoW is a transparent speedup wherever the filesystem offers it. (Note: modern .NET's `File.Copy` on Linux uses `copy_file_range`, which reflink-capable filesystems satisfy with a reflink — verify before reaching for P/Invoke.)

Deduplication follows the same philosophy: because blobs are plain files, proven filesystem-level dedup (`bees`/`duperemove` on btrfs, ZFS dedup) works underneath S3Harp, block-level and battle-tested, as an operator capability. Storage efficiency is the filesystem's craft; S3Harp's contribution is storing data in the plainest form that craft can work on.

### Metadata index seam

The index sits behind a domain-shaped interface in Core — operations like "put object record atomically", "ordered key range scan from a continuation point", "commit multipart upload". The contract speaks the domain's language throughout: atomicity and ordering guarantees are part of it, and persistence details stay inside each implementation.

The seam exists to serve exactly two implementations:

- **SQLite** (`Microsoft.Data.Sqlite`) — the real one: ordered range scans, atomicity, and durability in one dependency.
- **In-memory** — the test double that keeps the TDD loop fast and proves the seam honest.

S3Harp itself is the storage backend; the seam's job is testability.

## Engineering practice

These are requirements, enforced mechanically wherever possible:

- **Test-driven development is mandatory.** Every behavior starts with a failing test: red, green, refactor.
- **Test stack:** xUnit v3 on Microsoft.Testing.Platform — the native `dotnet test` mode in the .NET 10 SDK, selected via `global.json`, with `xunit.v3` as the sole test dependency. Assertions use xUnit's built-in `Assert`. Unit tests live per production project (`S3Harp.Core.Tests`, `S3Harp.Server.Tests`); `S3Harp.IntegrationTests` drives the real AWS SDK (`AWSSDK.S3`) against the in-process server — the compatibility oracle that defines "S3-compatible". Ceph's `s3-tests` conformance suite runs in CI as a ratchet: `tests/conformance/must-pass.txt` names the cases S3Harp passes, a listed case failing or an unlisted case passing fails the build, and the list only grows.
- **Target framework:** .NET 10 (current LTS), the single target for every project.
- **Idiomatic, well-written C#** and SOLID applied with judgment — interfaces at real seams, every abstraction earning its place.
- **Mechanical enforcement over convention:** `.editorconfig` and `Directory.Build.props` at the repo root with nullable reference types on, .NET analyzers enabled, and `TreatWarningsAsErrors` — the quality bar is a build failure, and so is a known vulnerability in any package restore pulls in, transitive ones included. CSharpier and Prettier own formatting; every style and code-quality rule the IDE analyzers offer is a build error, with the two the code deliberately departs from relaxed by name, and the code-quality analysis level is "all", with every rule the code departs from relaxed by name beside its reason, the culture-sensitive integer parse overloads are banned outright, reflection-based JSON serialization is switched off so every serializer call goes through a source-generated context, and the trim, single-file and native AOT analyzers are on, so the settings bind through generated code and validate in explicit checks.

## Implementation order

Each step ends with the AWS SDK exercising it, so compatibility is proven continuously:

1. Skeleton server returning correct S3 XML error responses (SDKs parse errors; this works first).
2. SigV4 verification — header scheme and chunked payloads.
3. Bucket create/list/head/delete.
4. Object PUT/GET/HEAD/DELETE with ETags and `x-amz-meta-*` metadata.
5. ListObjectsV2 with prefix, delimiter, and continuation tokens.
6. Multipart uploads, then CopyObject via the reflink path.

## Open questions

Deliberately open — each awaits an explicit decision:

- **Configuration surface** beyond the decided settings, which live in one validated `S3HarpOptions` record: `access_key_id` and `secret_access_key` (the root keypair, required at startup, whose id names the owner of every bucket) and `keys` (further keypairs with the same full access, held with the root pair in one credential store; per-key authorisation and reloading the list without a restart await decision), `data_dir` (the storage location, required), `bind` and `port` (loopback and 9000 by default: private unless asked, and the port local S3 tooling already points at) and `domain` (the virtual-hosted domain, `localhost` by default). Each setting has one name: it is the key in the settings file, the suffix of its `S3HARP_` environment variable and its command-line flag through System.CommandLine, with `--help` and `--version`; each source overrides the one before it in that order, and nothing else is a source: the framework's unprefixed environment provider is removed so a bare `PORT` or `DOMAIN` in the environment is not a setting. The settings file is read only when `config` names it, in the format its extension says: JSON through the framework's provider, TOML through a provider of S3Harp's own that walks Tomlyn's validated syntax tree into the same flat keys, so nothing binds by reflection and a redefined key is an error. A file that is missing or malformed stops the server with the parser's position. Framework logging sits at Warning and S3Harp's own at Information, overridable through the usual `Logging` keys. TLS is served in-process from `tls_cert` and `tls_key`, PEM only (what ACME clients and homelab CAs emit; PFX would need a password setting for a format the audience does not have): both or neither, the certificate file's first entry with the key and the rest as the chain Kestrel sends, and the listener is HTTPS only when they are set. A renewed certificate takes a restart; reloading it in place and client certificates await decision.
